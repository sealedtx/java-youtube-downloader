## Why 4.0

Baseline on 2026-11-19: 19 of 39 tests fail, every test that talks to YouTube.
Video info, playlists, search, subtitles, channel uploads and live streams are all broken. Only offline unit tests pass.
After phase 0 the same picture with `mvn test -Plive` (speed tests skipped): 18 of 24 live tests fail; one search test is flaky.

Root causes found with live probes (details in "Live findings"):

- Client profiles are hardcoded and stale (`ANDROID_VR` version `1.37` from 2022). YouTube answers stale clients with "Sign in to confirm you're not a bot".
- `visitorData` is never sent. Without it even a fresh client gets the bot check.
- The web client returns only SABR formats (no URLs), so the HTML watch-page fallback is useless for downloads.
- Playlists moved from `playlistVideoListRenderer` to `lockupViewModel`; the parser gets `null` and throws NPE. Search starts to show `lockupViewModel` too.
- Architecture makes every such change expensive: one 900-line `ParserImpl` mixes HTTP, JSON paths, callbacks and mapping; models take `JSONObject` in public constructors; global static state; no timeouts; retries corrupt files; all tests are live.

## Architecture principles

1. **Isolated features.** One extractor per feature (video, download, playlist/channel, search, subtitles). They share only infrastructure (HTTP, JSON helpers, innertube session). A broken search parser cannot break video info.
2. **Strategy chains with diagnostics.** Each feature tries several clients or endpoints in order and takes the first good answer. Every failed attempt is recorded (`attempts()`), for example `visionos: bot check; android_vr: HTTP 403`, so a bug report already shows the cause.
3. **Partial results instead of total failure.** A broken format or playlist item is skipped with a warning; the rest of the answer survives.
4. **Tolerant parsing.** A registry of renderer handlers (`lockupViewModel` next to the legacy renderers), alternative JSON paths, search for keys anywhere in the tree. Unknown items are skipped and counted.
5. **Client profiles are data.** Name, numeric id, version, user agent, context fields, and needs (JS player, PO token per context, cookies). Users can update or reorder them without a new release: `.clients(...)`.
6. **External needs behind small interfaces.** `HttpTransport`, `PoTokenProvider`, `ChallengeSolver`. If one is missing, only the clients that need it are skipped, not the library.
7. **No global state.** No `Authenticator.setDefault`, no static client priority, no static Base64 instance, no mutated enum constants.

## Public API sketch

```java
YoutubeDownloader yt = YoutubeDownloader.builder()     // or YoutubeDownloader.create()
        .proxy("127.0.0.1", 8080)
        .retries(2)
        .build();

VideoInfo video = yt.videoInfo("https://youtu.be/jNQXAC9IVRw");   // id or any YouTube URL
Format audio = video.formats().bestAudio().orElseThrow();
Path file = yt.download(audio, Paths.get("music"),
        DownloadOptions.defaults().onProgress(p -> System.out.println(p.percent() + "%")));

yt.videoInfoAsync(id).thenAccept(v -> ...);                   // CompletableFuture instead of callbacks
for (PlaylistVideo v : yt.playlist("PL...").videos()) { ... }  // continuations are fetched lazily
SearchResult r = yt.search(SearchQuery.of("nasa").type(TypeField.VIDEO));
String vtt = yt.subtitles(video.subtitles().get(0), SubtitleFormat.VTT);
```

- Sync methods plus `*Async` variants. `Request`, `Response`, `YoutubeCallback`, `Config` go away.
- Unchecked `YoutubeException` with subtypes (`VideoUnavailableException`, `BotCheckException`, `HttpException`, `ExtractionException`), each with `attempts()`.
- Immutable models, no JSON types in the public API. One `Format` class instead of four, and a `Formats` collection with `bestVideo`, `bestAudio`, `byItag`, `filter`.
- Per-call overrides through `yt.toBuilder()...build()` (shares caches).

## Feedback loop

| Level | Command | What it gives |
|---|---|---|
| Offline tests | `mvn test` (no network, under a minute) | Unit tests; end-to-end tests through the facade on recorded responses (fake `HttpTransport`); download tests against the JDK's built-in HTTP server (ranges, broken connections, 403/5xx, timeouts, cancel) |
| Fixture recording | `mvn test -Precord` (added in phase 2) | Re-records the reference corpus into gzipped fixtures; `git diff` shows what YouTube changed |
| Live checks | `mvn test -Plive` | One JUnit test per check (`LiveTest`): every client profile on its own, video cases (music, 4K, dubbed audio, short, long, ended stream, private, missing), full download, playlists, channels. Expectations with slack; known limitations are skipped, not failed; a removed reference video says "replace it in Corpus". Summary in `target/live-report.md` |

Everything runs locally (D10); there is no CI on GitHub.

Reference corpus (curated in phase 2): normal, long, live, upcoming, age-restricted, made-for-kids, private and deleted videos; short and long playlists, playlists with unavailable items, auto-generated playlists; channels by id, handle and legacy URL; search queries with filters and continuations.

Repair loop when YouTube changes something:

1. Live canary turns red.
2. Re-record fixtures (`-Precord`).
3. An offline test reproduces the failure.
4. Fix the mapper or, often, only the client profile data.
5. Offline and live are green again; commit.

This loop goes into CONTRIBUTING.md in phase 8.

## Phases

Every phase ends with a green `mvn test`, a short report with the live matrix, and its own commits on `refactoring-4.0`. Push, tags and changes on `master` need explicit approval.

### Phase 0: groundwork and test loop (done)

- `pom.xml`: version `4.0.0-SNAPSHOT`, Java 11, current compiler and surefire plugins, JUnit 5.14, Mockito 5, logback only in test scope, profile `live`.
- Network tests tagged `@Tag("live")`; `mvn test` runs offline.
- This document. (GitHub workflows were added and then removed again, see D10.)

Done when: `mvn test` is green without network; `mvn test -Plive` shows the "before" state.

### Phase 1: core infrastructure

- Own JSON parser and writer (D2) with null-safe navigation (`JsonNode`): paths, alternative paths, recursive key search, lenient number/string conversion, parse a JSON value that starts at an offset inside HTML (no regex for `ytInitialData`), nesting limit.
- `HttpTransport` interface (named so it does not clash with `java.net.http.HttpClient`; request and response are nested types) and a default `UrlConnectionTransport`: connect and read timeouts, gzip, only `http`/`https` URLs, proxy and proxy auth per connection (no global `Authenticator`).
- Internal `Http` on top of any transport: `RetryPolicy` (backoff with jitter, retry on I/O errors, timeouts, 408, 429 and 5xx, honor `Retry-After`, never retry other 4xx), response size limit for text, status errors with a short body snippet.
- Tokens, signatures and the client IP masked in URLs used in messages and logs.
- Strict parsing of video ids and URLs: watch, youtu.be, shorts, live, embed, music, nocookie.
- Build only what the video slice needs; add the rest when a feature needs it (playlist and channel id parsing lands in phase 4, text helpers for `runs`/`simpleText` in phase 4, the public exception hierarchy in phase 2 because the name `YoutubeException` is taken by the 3.x class until phase 2 deletes it).

Done when: unit tests cover all of the above (fake HTTP server for timeouts, retries, gzip, size limit).

### Phase 2: video info works again + new public API

- Delete the 3.x API and internals (`Request*`, `Response*`, callbacks, `Config`, `Parser*`, `Extractor*`, `DownloaderImpl`, `Clients`, `ClientType`, `cipher/*`) and fastjson. Keep the `Itag` table, quality enums and search parameter encoding.
- `ClientProfile` data ported from yt-dlp `INNERTUBE_CLIENTS`; default JS-less chain `visionos -> android_vr -> ...`, ordered by the live matrix.
- `InnertubeSession`: `visitorData` from the home page `ytcfg`, cached, refreshed after a bot check; correct headers per profile (`User-Agent`, `X-YouTube-Client-Name`, `X-YouTube-Client-Version`, `X-Goog-Visitor-Id`).
- `VideoExtractor`: client chain, playability classification (OK, bot check, login, age, unplayable, error), formats (skip SABR-only formats and formats that need a solver, with warnings), details, captions, HLS/DASH manifest URLs. Formats with the same itag (several audio tracks) are kept apart.
- Public exception hierarchy: unchecked `YoutubeException` and subtypes, each with `attempts()`.
- URLs taken from YouTube responses are used only if they are `https` on YouTube or Google video hosts.
- Immutable models, facade, `videoInfo` / `videoInfoAsync`.
- Fixture recorder (`-Precord`), offline tests on fixtures, live canary per client with `target/live-report.md`.
- **Checkpoint:** review the API on working code before it is copied to other features.

Done when: video info works live for the reference corpus (except expected restrictions), offline tests are green.

Result (2026-11-19): live matrix green for `visionos` and `android_vr` (formats, subtitles, 64 KB range download of the best audio); private and missing videos give `VideoUnavailableException`. Notes:
- `visitorData` comes from `sw.js_data` (2.8 KB; the home page is the fallback). That response also holds the caller's IP, so the fixture recorder masks it.
- Without a JS runtime `visionos` still gives up to 2160p (checked on 4K videos); N3WPORT simply has no more than 720p. Not served without a JS runtime: "made for kids" videos.
- The live and age-restricted examples from older tests and from yt-dlp are deleted on YouTube; live handling is covered by hand-written answers for now. The corpus lives in `testing/Corpus`.
- Search parameter encoding moved to `internal.SearchParams` (plain base64; innertube takes it in JSON, so no URL encoding).

### Phase 3: download engine

- Sequential range requests (`&range=`, 10 MB chunks by default); after a broken connection continue from the last byte, never duplicate bytes.
- Write to `<name>.part`, atomic move on success; create with `CREATE_NEW`, unique names; safe file names (path separators, Windows reserved names, length); check the final size against `contentLength`.
- Progress (bytes, total, speed), cancel through the returned future.
- Clear error when a format URL has expired: fetch video info again.

Done when: every path is covered by tests against a local HTTP server; small formats download live.

Result (2026-11-19): `download(format, file[, options])`, `download(format, outputStream, options)`, `downloadAsync` (cancel interrupts the work; `videoInfoAsync` uses the same task). Retry budget is per chunk; a resumed chunk starts at the first missing byte. Each range request sends the user agent of the client profile that returned the URL. `FileNames.safe`/`of` build safe names from titles. Live: full download of the best audio and video of the zoo video, sizes match.

### Phase 4: playlists and channels

- Innertube `browse` (JSON) for the first page and continuations; `ytInitialData` from the HTML page as fallback strategy.
- Renderer registry: `lockupViewModel`, `playlistVideoRenderer`, `continuationItemRenderer`.
- Lazy `videos()` so playlists with thousands of items do not sit in memory.
- Channels: `@handle`, `UC...`, `/c/...`, `/user/...` resolved to the uploads playlist `UU...`.

Result (2026-11-19): `playlist(idOrUrl)` and `channelUploads(channel)` return a `Playlist` with lazy `videos()`/`stream()` and `allVideos()`. Browse runs as the `WEB` profile (`builder().webClient(...)` to change it). Items are collected by renderer name only inside `contents` (first page) or `onResponseReceivedActions` (later pages); a repeated continuation token ends the paging. Missing playlists give `PlaylistUnavailableException` (from YouTube's error alert), unknown channels `ChannelUnavailableException`. Live: #AskNASA 22/22, album 13/13, NASA uploads 250 of 6207 in about 3 s. Fixtures now cover browse, continuations, resolve_url and the web page (only its `ytInitialData` is stored), 280 KB in total.

### Between phases 4 and 5: broader live checks (done)

`LiveCanaryTest` (one test, failed only if nothing worked) became `LiveTest` with 19 separate tests on a wider corpus (`testing/Corpus`). First run (2026-11-19): 18 OK, 1 known limitation (made for kids). Still missing from the corpus: a video that is live right now and an age-restricted one (older examples are deleted on YouTube); both are covered by hand-written answers offline.

### Phase 5: search

- Innertube `search` (JSON); one code path for the first page and continuations.
- Filters through the existing parameter encoding (already tested).
- Item registry (videos, channels, playlists via `lockupViewModel`, shelves, shorts), suggestions, refinements.

Result (2026-11-19): `search(text)` / `search(SearchQuery)` give a `SearchResult` page with `items()`, `videos()` (shorts flagged with `isShort()`), `channels()`, `playlists()`, `estimatedResults()`, `correctedQuery()`, `refinements()` and `nextPage()`. Shelves are flattened in place; ads and "key moments" carousels are skipped; a page that points to itself ends the paging. Channel handle and subscriber count are read by content because YouTube swaps their fields. List-page helpers (collect, owner, thumbnails, durations, counts like "2.8M") moved to `internal.youtube.Renderers`, shared with playlists. Live: mixed results over two pages, type filters, duration filter, spelling correction and exact search. Not seen live yet: `searchRefinementCardRenderer`, so `refinements()` is usually empty.

### Phase 6: subtitles

- Tracks from the player response, format via `fmt=`, translation via `tlang=`.
- Remove the dead `video.google.com/timedtext` list endpoint.
- Skip tracks whose client needs a subtitles PO token when no provider is set.

Result (2026-11-19): `subtitles(track, format)` and `subtitles(track, format, translateTo)`; `SubtitleFormat` VTT, SRT (YouTube serves it natively), TTML, JSON3, SRV1-3; `SubtitleTrack.url(format[, translateTo])` for other download tools. Only YouTube hosts are fetched; language codes are validated. The old list endpoint was already gone with the 3.x code. Known limitation: since 2026-11 YouTube answers machine translations (`tlang`) with HTTP 429 for the JS-less clients, while plain tracks work; the error says so and the live check reports it as skipped. No track needed a PO token with the default clients, so nothing is skipped for that yet (phase 7a).

### Phase 7a: PO token provider SPI (later)

- `PoTokenProvider` interface: request with context (GVS, PLAYER, SUBS), client, `visitorData`, `videoId`; returns a token. In-memory cache with TTL.
- Profiles that need tokens become usable when a provider is set. The library never generates tokens itself (see BotGuard in the glossary).

Experiment (2026-11-19) with a real token provider (bgutil-ytdlp-pot-provider 2.0.2 in Docker; token in 1.5 s, bound to the video id, valid about 6 h), video `jNQXAC9IVRw`:

| Check | Without token | With token |
|---|---|---|
| Translated subtitles (`tlang=uk`), visionos or web track URL | 429 | 429 (video- and visitor-bound token, `pot`+`potc`) |
| web / mweb player without `signatureTimestamp` | UNPLAYABLE "page needs to be reloaded" | same |
| web / mweb player with `signatureTimestamp` | OK, SABR only | OK, SABR only |
| tv_samsung player with `signatureTimestamp` | OK, 15 formats with URL | same |
| tv_samsung audio range | 403 | 403 (URLs carry an `n` parameter that only the JS challenge can rewrite) |

Conclusion: on its own a PO token unlocks nothing for this library today. What blocks the other clients is the `signatureTimestamp` (cheap: a number from the player JS) and the `n` challenge (phase 7b); web and mweb stay SABR-only either way. 7a only pays off together with 7b, and for translated subtitles neither helps (likely needs a login, 7c). Decision: postpone 7a until 7b exists.

### Phase 7b: JS challenge solver (later)

- `ChallengeSolver` interface (signature and n, batch requests, `isAvailable()`).
- Implementation that runs an external JS runtime (Deno, Node or QuickJS) through `ProcessBuilder` with the vendored yt-dlp EJS solver scripts (Unlicense), pinned version and checksum, no remote code. JVM only.
- Player JS download and cache per player version; `signatureTimestamp` in player requests.
- Unlocks `tv_samsung` and `web` style clients: more formats, likely higher quality.

### Phase 7c: cookies / logged-in session (later)

- Netscape cookies file or cookie string; `SAPISIDHASH` authorization for innertube when logged in.
- Unlocks age-restricted videos and helps against the bot check. Cookies are secrets: never logged.

### Phase 8: release 4.0 (later)

- README for 4.0, MIGRATION.md (3.x -> 4.0 table), CHANGELOG, CONTRIBUTING.md (repair loop above).
- Final review, dependency check, javadoc for the public API.
- `4.0.0-rc1` via JitPack after approval for push and tag, then `4.0.0`.

## Non-goals

- SABR streaming: undocumented binary protocol; even yt-dlp has it only on an experimental branch.
- Muxing video and audio (D6).
- OAuth login: YouTube blocked it for third-party clients.
- Generating PO tokens inside the library: needs BotGuard in a real browser environment; only the SPI (7a).

## Glossary

- **Innertube**: YouTube's internal JSON API (`/youtubei/v1/player`, `browse`, `search`, `next`), used by all official apps. Each request carries a client context (client name, version, device fields).
- **Client profile**: one official app identity (web, TV, Android VR, visionOS, ...). YouTube treats each one differently: which formats it gets, whether it needs a JS player, PO tokens or cookies. Old versions get the bot check.
- **visitorData**: an anonymous session id from YouTube (`VISITOR_DATA` in `ytcfg`). Sent in the context and as `X-Goog-Visitor-Id`. Without it requests get "Sign in to confirm you're not a bot".
- **GVS**: Google Video Servers (`*.googlevideo.com`), where the media bytes come from.
- **SABR** (Server ABR, server-side adaptive bitrate): the streaming protocol of the web player. Instead of one URL per format, the player sends POST requests with a protobuf description of its state (buffer, bandwidth, wanted formats) to `serverAbrStreamingUrl`; the server decides which media chunks to return and sends them in its own binary container (UMP). Formats of SABR-only clients have no `url`, so they cannot be downloaded with plain range requests.
- **JS challenges (signature, n)**: some clients return obfuscated URL parameters. `signatureCipher` must be decoded and the `n` parameter transformed by functions hidden in the player JavaScript (`base.js`), otherwise the URL returns 403 or is throttled. yt-dlp now solves both only in a real JS runtime (EJS scripts on Deno, Node or QuickJS).
- **PO token** (Proof of Origin): a token that proves a request comes from a genuine YouTube client. Used in player requests (`serviceIntegrityDimensions.poToken`), in stream URLs (`pot=`) and in subtitle requests. Bound to a session (`visitorData`) or, for most GVS tokens, to the video id; lifetime can be as short as about 12 hours; a web token does not work for Android or iOS clients.
- **BotGuard**: Google's anti-bot system. In the browser it is a heavily obfuscated program for a virtual machine written in JavaScript, changed often by Google. It checks the environment (DOM, browser APIs, timing) to tell real browsers from scripts. Its result is exchanged with Google's anti-abuse API for an integrity token, from which the page mints PO tokens. Android and iOS apps use platform attestation instead. Running BotGuard needs a real browser or a convincing emulation (Node with jsdom, Android WebView), which Google keeps detecting; that is why the library only offers an SPI.
- **OAuth (context)**: around 2023-2024 tools could log in like the YouTube TV app (OAuth device flow: enter a code at google.com/device). Late in 2024 YouTube blocked this for third-party clients; yt-dlp removed it and its wiki says OAuth login no longer works. Login today means browser cookies (phase 7c).
